# Лабораторная работа: RAG-ассистент по документам

Вопросно-ответная система по базе знаний статей русской Википедии на тему **«Космос»**.  
Система находит релевантные фрагменты документов и формирует ответ с указанием использованных источников. RAG и порог сходства снижают риск галлюцинаций, но не гарантируют фактическую корректность: ответы необходимо проверять по источникам.

---

## 1. Стек технологий и архитектура

В соответствии с регламентом лабораторной работы, реализация выполнена **без высокоуровневых фреймворков** (LangChain, LlamaIndex): чанкинг, построение поисковых индексов, гибридный поиск и сборка RAG-промпта написаны вручную на чистом Python.

| Компонент | Выбранное решение | Описание |
|---|---|---|
| **Язык и среда** | Python 3.12, Jupyter | Автономный запуск на обычном ноутбуке без GPU |
| **Корпус** | 35 статей Википедии («Космос») | 153 638 слов (~559 страниц standard print) |
| **Чанкинг** | Скользящее окно (Word-level) | Размер 400 слов, перекрытие (overlap) 50 слов, 451 чанк |
| **Эмбеддинги** | `intfloat/multilingual-e5-small` | 384-мерные векторы, префиксы `passage: ` и `query: ` |
| **Векторный индекс** | `FAISS` (`IndexFlatIP`) | Косинусное сходство по нормализованным векторам |
| **Лексический поиск** | `rank_bm25` (`BM25Okapi`) | Полнотекстовый baseline поиск по токенам |
| **Гибридный поиск** | Hybrid RRF | Reciprocal Rank Fusion ($k=60$) объединяет BM25 и FAISS |
| **Генерация ответа** | Ollama (`qwen2.5:3b`), TokenWave API / экстрактивный fallback | Серверный ключ TokenWave берётся из `.env`; при ошибке провайдера включается резервный экстрактивный режим |
| **Интерфейс** | Gradio | Интерактивный веб-интерфейс в браузере |

## 3. Инструкция по запуску

### Быстрый старт на локальном компьютере

1. **Клонируйте репозиторий и перейдите в папку проекта:**
   ```bash
   cd RAG-Document-Assistant
   ```

2. **Установите зависимости:**
   ```bash
   pip install -r requirements.txt
   ```

3. **Запустите Jupyter Notebook:**
   ```bash
   jupyter lab
   # или
   jupyter notebook
   ```
   Откройте файл `notebooks/RAG_Document_Assistant.ipynb` и выполните **Kernel -> Restart Kernel and Run All Cells**. Результат выполнения зависит от доступности модели эмбеддингов, локальной Ollama и сетевого API; в репозитории не заявляется успешный запуск без свежего прогона.

5. **Проверка кода и корпуса:**
   ```bash
   python -m pip install pytest pandas requests numpy
   python -m pytest -q
   python src/validate_corpus.py
   ```

4. **(Опционально) Подключение локальной LLM через Ollama:**
   Если вы хотите генерировать ответы через локальную нейросеть:
   ```bash
   ollama run qwen2.5:3b
   ```
   Если Ollama недоступна или завершилась ошибкой, система использует экстрактивный резервный режим и явно сообщает об этом в ответе.

## 4. Результаты экспериментов и ограничения оценки

Метрика **Hit@k** оценивает только попадание целевого документа в первые k результатов поиска. Она не подтверждает правильность текста ответа, полноту фактов или корректность цитирования.

Таблица результатов ниже — исторические значения предыдущего прогона, а не подтверждение текущей версии. Для получения актуальных цифр выполните ноутбук сверху вниз; он сохранит результаты в `results/eval_generation_latest.csv` и `results/chunking_experiment.csv`.

| Метод поиска | Исторический Hit@1 | Исторический Hit@3 | Исторический Hit@5 |
|---|---:|---:|---:|
| BM25 | 75% (15/20) | 95% (19/20) | 100% (20/20) |
| FAISS | 85% (17/20) | 100% (20/20) | 100% (20/20) |
| Hybrid RRF | 90% (18/20) | 100% (20/20) | 100% (20/20) |

**Важно:** сохранённый ранее прогон генерации содержал три ответа, размеченных как «Галлюцинация». Поэтому утверждение о 100% корректных отказов удалено. Новая оценка показывает фактический FAISS score, применённый порог, наличие отказа и эталонный ответ. Для вопросов в корпусе фактическая корректность намеренно не маркируется автоматически как «Верно»: требуется ручная проверка ответа и подтверждающей цитаты.

### Эксперимент с чанкингом

Ноутбук запускает матрицу 3×3: `chunk_size = 300, 400, 500` и `overlap = 30, 50, 100`. Для каждой конфигурации чанки и индексы строятся заново, затем рассчитываются Hit@1/3/5. До запуска и анализа этого эксперимента нельзя утверждать, что конфигурация 400/50 оптимальна.

### Порог отказа

Порог FAISS 0.70 является предварительной эвристикой, а не вероятностью уверенности. Векторное сходство зависит от модели, корпуса и формулировки вопроса. Ноутбук выводит распределения score для вопросов in-corpus и OOD; надёжная калибровка требует отдельной и более широкой размеченной выборки.

### API-ключ и режимы генерации

TokenWave API поддерживается, хотя ранее не был отражён в README. Ключ читается только на стороне Python-процесса из `.env`; он не должен передаваться в значения Gradio-компонентов, примеры или клиентский интерфейс. Если ранее использовавшийся ключ был опубликован или передавался в браузер, его следует отозвать и выпустить новый.

## 5. Шпаргалка: Ответы на вопросы к защите

### Общее
* **Что такое RAG и какую проблему LLM он решает?**  
  *Ответ:* Retrieval-Augmented Generation — подход, при котором перед генерацией ответа система ищет релевантные фрагменты в базе знаний и передаёт их модели. Это помогает актуализировать ответы и снизить риск галлюцинаций, но не устраняет их полностью и не гарантирует корректность без проверки источников.
* **Чем RAG лучше и хуже дообучения (Fine-tuning)?**  
  *Ответ:* RAG позволяет обновлять базу документов без переобучения весов и при корректной реализации показывать источники. Он сам по себе не гарантирует точность ссылок и не защищает от утечки данных: конфиденциальность зависит от хранения, доступа и передачи данных внешним провайдерам. Fine-tuning адаптирует стиль и поведение модели, но сам по себе также не гарантирует фактическую точность.
* **Из каких компонентов состоит ваша система?**  
  *Ответ:* 1) Document Loader & Chunker (подготовка данных); 2) Embedder (`multilingual-e5-small`) и Indexer (`FAISS` + `BM25`); 3) Retriever (гибридный поиск RRF); 4) Generator (RAG-промпт + LLM Ollama/экстрактивный режим); 5) Evaluator (замер Hit@k).

### Чанкинг
* **Как выбран размер чанка (400 слов, 50 оверлап)?**  
  *Ответ:* Размер чанка не объявляется оптимальным заранее. В ноутбуке предусмотрен сравнительный эксперимент 3×3: 300/400/500 слов и overlap 30/50/100; выбор конфигурации делается по фактическим Hit@k и качеству ответов.
* **Зачем нужен оверлап?**  
  *Ответ:* Чтобы факт или предложение, оказавшееся на границе разреза двух чанков, не разорвалось по смыслу.
* **Какие ещё стратегии разбиения существуют?**  
  *Ответ:* По предложениям (Sentence splitting), рекурсивное разбиение по иерархии символов (`\n\n`, `\n`, `.`), разбиение по заголовкам Markdown/HTML и семантический чанкинг по падению косинусного сходства между соседними предложениями.

### Эмбеддинги и поиск
* **Что такое эмбеддинг текста?**  
  *Ответ:* Плотный числовой вектор фиксированной размерности (в нашем случае 384), отражающий семантическое значение текста в многомерном пространстве. Близкие по смыслу фразы имеют близкие векторные координаты.
* **Почему косинусное сходство, а не евклидово?**  
  *Ответ:* Косинусное сходство оценивает угол между векторами, игнорируя их абсолютную длину (норму). Если векторы нормализованы к единичной длине ($||v||=1$), косинусное сходство прямо пропорционально квадрату евклидова расстояния ($||u-v||^2 = 2 - 2 \cos(u,v)$).
* **Зачем модели e5 префиксы `query: ` и `passage: `?**  
  *Ответ:* Архитектура семейства e5 обучалась как асимметричный биоэнкодер: префикс явно сообщает модели, кодирует ли она короткий поисковый запрос пользователя или длинный справочный фрагмент документа. Без префиксов качество поиска резко деградирует.
* **Как работает BM25 и почему он дополняет векторный поиск?**  
  *Ответ:* BM25 оценивает частоту терминов с насыщением (TF) и штрафом за частые слова (IDF) с нормализацией длины документа. Он превосходит векторный поиск на редких именах собственных, аббревиатурах, номерах моделей и кодах («SN 1054», «G2V», «ТМ-32»).
* **Что такое гибридный поиск и Reciprocal Rank Fusion (RRF)?**  
  *Ответ:* Объединение результатов двух разных поисковиков. RRF вычисляет итоговый ранг кандидата как сумму $\sum \frac{1}{60 + \text{rank}_i}$, что не требует нормализации шкал скоров BM25 и FAISS.
* **Как FAISS ускоряет поиск?**  
  *Ответ:* В базовом варианте `IndexFlatIP` он выполняет точный поиск через векторные инструкции SIMD (AVX/BLAS). В приближенном режиме (ANN: IVF, HNSW) он разбивает пространство на кластеры или строит граф соседей, позволяя искать по миллионам векторов за единицы миллисекунд.

### Генерация и промпт
* **Как устроен промпт?**  
  *Ответ:* Четкая системная роль + строгая инструкция опираться только на контекст + нумерованные фрагменты `[1]`, `[2]` + вопрос + правило честного отказа при нехватке данных.
* **Почему нельзя ставить $k=50$?**  
  *Ответ:* Это приводит к переполнению контекстного окна («Lost in the Middle»), замедлению генерации, росту стоимости инференса и повышению риска галлюцинаций из-за фонового шума.
* **Как система понимает, что ответа нет?**  
  *Ответ:* Двухуровневый контроль: 1) Фильтр по порогу косинусного сходства (confidence threshold) отсекает запросы, у которых нет близких векторов в базе; 2) Системный промпт инструктирует модель явно признавать отсутствие ответа.
